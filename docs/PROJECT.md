# Agent Harness 项目说明

本文记录项目的目标、边界和开发原则。阶段安排见 [ROADMAP.md](ROADMAP.md)，实际进度以 [PROGRESS.md](PROGRESS.md) 为准。

## 项目定位

构建一个以 TypeScript 为主语言、面向 Windows 原生运行的 Agent Harness，从最小 Agent Loop 起步，逐步形成支撑本地 Agent 任务执行的基础能力。

项目名称为 Fatcat。这是一个独立新项目。

近期定位为能够实际修改代码、运行验证并交付可 review 结果的本地开发 Agent；固定临时样例已跑通读取、修改、执行测试及报告的最小闭环，尚不代表复杂开发任务的成熟度。保持通用 Harness 的演进空间，但由本地开发任务驱动近期取舍。达到 LoopX 和 OpenViking 对应能力的水平是长期目标，按选定版本、能力范围和实际任务逐步验收。

先完成一个可运行、可验证的闭环，再根据实际任务暴露的问题演进。不以差异化或功能数量为目标，也不在首版中预建长期架构。

在用户指定的 `feat/webui-dev` 继续改进本地交互：会话变更采用页面中央弹窗，服务启动后自动打开默认浏览器。composer 分为消息和底部工具栏，左侧模式/带框工作区，右侧无框上下文/模型/发送；窄屏按组换行。会话列表仅显示名称，轮次和日期移入悬浮提示。权限菜单展示顺序为 Plan、Manual、Accept edits、Free to go。上下文仅依据最近父请求的实际输入 token 与已核对的模型窗口，不替代请求字节预算或累计模型消费。界面固定英文，多语言切换列为后续计划；不改写运行时用户数据或增加语言框架。验证事实见 PROGRESS。

`feat/webui-beauty` 在已合入 PR #22 的 main（`05b4e22`）上统一 Web UI 视觉：暖灰/柔绿主题、居中的欢迎语与 composer、输入框下方的建议操作、清晰的会话与消息间距、本地 Lucide SVG 图标和深浅色/窄屏布局。会话行省略号复用原右键菜单，移动侧栏增加遮罩关闭；不改变 Session、Loop、工具或授权语义，也不增加依赖。

`feat/webui-dev` 后续修正空会话生命周期：默认启动、New chat 和删除活动会话只进入未保存欢迎页，首条消息在执行前保存；显式命名、分支和恢复保留原语义。草稿仍由共享 SessionManager 持有，不增加浏览器独立会话存储，不自动清理既有空会话，也不改变 CLI / TUI 默认创建行为。

同分支增加权限模式和独立 `src/permissions/`，与 session 同级集中审批及文件、文本、进程和网络执行 guard。Manual 逐项审批，Accept edits 自动允许受控工作区修改且命令仍审批，Plan 只读规划并禁止写入/命令；Free to go 开放当前用户权限内的工作区外文件及 HTTP(S) 地址/端口，普通命令自动执行，危险/不透明命令经一次审批。CLI / chat / TUI 可从启动选项选定，Web UI 空闲时切换；父子使用同一运行时策略，显式启动 read-only/shell-deny/web-deny 为上限。前三种保持原范围和执行规则，旧 allow 参数不隐式选择 Free；命令判断是保守启发式，不能分析所有脚本内部操作，不提供 OS 沙箱。保持原工具与会话职责，详见 [权限架构](ARCHITECTURE/PERMISSIONS.md)。

2D-10 在同阶段、同分支补充按已有 subsystem 组织的内置 Skills，存放于 `src/skill/<subsystem>/<skill-name>/SKILL.md`，经构建随程序分发并以最低优先级发现。当前提供工作目录编辑、独立委派、上下文恢复、验证交付四种任务指导；用于 Fatcat 帮助用户处理目标项目，不是 Fatcat 自身源码维护规范。继续复用现有加载、Session 和权限边界，后续仅按实际 subsystem 任务扩充内容，不建空目录或搬迁运行时模块。内置补充已通过离线验收，真实模型效果尚未验证。

按用户本轮明确要求，阶段 2D-11 在 `feat/tui-dev` 增加可选 `--tui` 终端界面，提前进入此前后移的 TUI 范围。目标是让模型、工作路径、权限、回合状态、请求预算、实际 token 用量和 provider 返回的缓存命中信息可见；保留原单次 CLI 与 `--chat`。视图、交互控制和统计分开，继续复用 Session、Loop、工具及审批边界。TUI 采用 TypeScript 的 pi-tui 组件，界面参考 pi 与 Charm 的终端布局；没有更换 Node、pnpm 或模型 SDK。实现与验证状态以 PROGRESS.md 为准。

同阶段在 `fix/default-workspace-tools` 修正日常入口：普通任务、`--chat`、`--tui` 默认使用启动目录，`--workspace` 仅负责覆盖目录。read、write、shell 作为同级工具默认提供，写入与命令继续逐次确认，显式权限策略保持有效。规范工作目录作为父子模型的请求指导并供 TUI 显示，使模型可直接回答当前路径；不新增模型工具，不改变成功历史或程序化 createTools 的显式目录与只读默认边界。验证事实以 PROGRESS.md 为准，不据此扩大阶段范围。

启动目录指用户调用命令的位置。pnpm start 通过专用启动器恢复 pnpm 的调用目录，避免包脚本自动切回包根影响默认工具范围；相对 --workspace 也按调用位置解析。构建及 .env 加载仍在包根，直接执行编译 CLI 则使用自身 cwd；这只是入口修正，不新增工作目录发现或权限子系统。

交互命令层继续保持简单：chat / TUI 使用共享本地分发，`/skills` 展示已发现元数据，`/sessions` 列出所选工作目录会话，不发送模型请求或加载完整技能正文。原技能/会话列表启动参数已移除，交互启动仍使用正常 provider 配置；bare `--resume` 保留无凭据列表与选择行为，Web UI 会话侧栏不变，不增加其斜杠技能命令。

规划采用逐步细化的方式：当前阶段明确范围和验收条件，后续阶段只保留目标、边界和验收方向。进入下一阶段前，再结合已有实现与验证结果决定具体任务；暂不安排详细排期、类结构或完整接口体系。

按用户要求在 `feat/webui-dev` 分两步加入工作区 HTML/SVG 能力。第一步为自包含单文件的用户预览、刷新及隔离运行区域。第二步已实现共享 `browser` 工具：Playwright 打开本地页面和相对资源、执行基本交互、采集错误与 DOM/SVG 几何状态、保存 JSON/PNG 证据，并接入 CLI/TUI/Web UI 审批和回合报告。模型可据文本状态调用 write 修复并重新检查；Web UI 可查看证据。浏览器执行沿用 shell 权限上限，始终限工作区，无外部站点或开发服务器访问。图像输入和多时刻动画分析仍为后续计划；实现边界见 [BROWSER.md](ARCHITECTURE/BROWSER.md)，验证事实见 PROGRESS。

## 基本约束

本轮在用户指定的 `fix/session-perfection` 增加阶段 2D-12 公开联网查询：一个通用 web 工具支持搜索与已知 URL 读取，默认向 CLI / chat / TUI 提供，并配套资料/新闻研究与天气查询 Skills。网络权限独立于文件写入权限，可用 `--web-permission deny` 关闭。功能限公开、有界、可取消的只读 HTTP(S) 请求，继续复用既有 Loop、Session、模型 SDK 和委派边界；不扩展为浏览器、爬虫、Web UI 或新模型供应商。实际实现及离线/在线验证见 PROGRESS.md。

- 主语言为 TypeScript，首版面向 Windows 原生运行，不以 WSL、Docker 或远端服务器为前提。
- docs/ 之外的仓库文本文件统一使用英文，包括源码、注释、测试、提示、脚本、配置、README.md 和 AGENTS.md；中文只允许出现在 docs/ 下。运行时用户输入与模型输出不受此文件语言约束。
- 运行时、包管理器和模型 SDK 优先沿用本项目仓库已有选择；如果没有，则在实现开始时选择简单、稳定、适合当前目标的方案，并在 docs/ARCHITECTURE/ 下的相关文档中记录理由。
- 当前工程采用 Node.js 24、pnpm 11 和 TypeScript；DeepSeek 为默认模型服务，新增 Kimi、MiMo 和 Qwen。模型客户端沿用 openai 兼容 SDK；每次进程启动选择一个供应商，具体协议和开发规范见 [PROVIDERS.md](ARCHITECTURE/PROVIDERS.md)。
- 先实现简单 Loop，不同时建设 Graph 引擎。
- 第一阶段曾只接入 DeepSeek；本轮用小型供应商配置描述协议差异，保持模型调用、循环控制与工具执行的边界清晰，不增加运行时插件注册表、自动路由或复杂供应商框架。
- 任务执行以本机为中心，远端任务暂不考虑。所选模型通过对应厂商在线 API 接入，模型服务调用不等同于远端任务执行。

## 第一阶段：最小 Agent Loop

目标是完成以下闭环：

CLI 用户输入 → 模型响应或提出工具调用 → 执行工具 → 将关联结果回传模型 → 继续循环 → 输出最终结果并结束。

第一阶段只包含：

- CLI 接收用户输入并输出最终结果。
- 一个模型接入，以及单次运行内的内存消息历史。
- 一个无副作用的示例工具，用于验证工具调用闭环。
- 工具调用与结果的正确关联，并在后续模型请求中保留必要历史。
- 基本参数校验与错误处理。
- 最大迭代次数限制，以及能确认执行过程和结束原因的必要日志。
- 可复现的 Windows 安装、配置、运行和验证说明。

完成标准是闭环实际可运行，而不只是有代码骨架或设计方案。既要验证直接回答，也要验证模型调用工具后根据结果继续回答；异常和达到迭代上限时应能明确结束。具体用例在实现时补充，真实模型验证与模拟验证须分别记录。

## 当前非目标

阶段 2D-9 的临时多文件双回合验收保留为回归基线。2D-10 的本地 Skills 与供应商选择继续使用已有历史和权限边界：启动发现元数据，模型按任务通过通用 read 加载 SKILL.md 和引用资源；成功历史保留已加载指令，失败丢弃本轮未完成模型历史。Skills 不授予读写或命令权限，也不自动安装或执行脚本。供应商在本次启动固定，不加入回合中切换、模型路由、流式输出或思考历史管理。2D-14 将会话持久化与管理纳入当前范围；完整 Task、分层 Context、长期记忆、文件检查点和操作恢复仍不进入本轮范围。

当前保留 CLI，并提供可选 TUI 与本地 Web UI。阶段 2D-13 在最新 main 的 `feat/webui-dev` 提前实现 `pnpm start --webui`：参考 ChatGPT 网页的侧栏、会话和底部输入布局，复用 Session、Agent Loop、工具权限和回合报告；本地 HTTP 与浏览器交互分层，不新增 Agent 运行时。首版仅监听本机；2D-14 在该边界内补充持久会话列表与切换，各标签仍共享一个活动会话、顺序执行回合，不提供远程部署或模型流式协议。验证事实见 PROGRESS.md，设计见 [WEBUI.md](ARCHITECTURE/WEBUI.md)。Channel、App 继续后移；Hooks、MCP、后台任务与 Cron 按实际需求引入。完整长期记忆、复杂调度、递归委派和 Graph 引擎不进入近期范围。

不为未来功能预建大量空接口，不把参考项目整体搬入本项目，不在任务成功率尚无明确标准时以 token 成本最小化作为优先目标。

以上是当前范围边界，不代表这些能力永远不做；是否引入、何时引入，以后续阶段的实际需要为准。

## 长期演进方向

1. 跑通基本 Agent Loop，建立最小可验证基线。
2. 优先完成本地开发闭环，围绕工具使用补齐必要权限、Session、Context 和 Task 能力；交互使用 CLI、可选 TUI 和本地 Web UI，其他入口后移。
3. 吸收 LoopX 的目标、进度、关卡与证据管理理念，以及 OpenViking 的上下文组织、分层加载与记忆理念，原生实现本项目所需能力。
4. 完善决策可观测、执行路径可回溯与执行可恢复能力。
5. 在明确的任务成功率门槛下优化 token 成本。

这些是演进方向，不是本轮功能清单，也不是对参考项目内部设计的采用结论。相关项目的具体机制应在进入对应阶段时调研和取舍。

## 开发原则

- **先完成，再完善。** 每一阶段先交付可用闭环，再根据证据提高质量。
- **保持简单。** 只为当前需求建立抽象，避免提前建设复杂框架。工具优先采用少量通用、可组合的能力入口，例如 read、write 和命令执行，避免为每种开发操作增加专用工具。
- **任务驱动能力选择。** 目标行为是由 Agent 根据任务选择工具和是否委派，日常使用不依赖用户逐项开启内部子系统。能力可用性、工作目录授权、执行权限、预算与取消由 Harness 约束；自动选择不等于无限授权。阶段 2D-4 已完成 CLI 默认委派迁移，模型选择行为仍需通过实际任务持续评估。
- **维护清晰组织。** CLI / TUI / Web UI 负责交互，Loop 负责控制，模型客户端负责通信，工具负责执行；状态与权限各自具有明确所有者。少量工具入口不意味着把所有实现放入一个大函数。保持可读、可维护、可扩展，避免为未来预建空接口。
- **逐步演进。** 每次改变有明确目的、范围和可观察结果，不一次性塞入长期目标。
- **以验证支持结论。** 区分计划、已实现和已验证；未执行的验证不能写成通过。
- **持续追求质量。** 围绕正确性、错误处理、可读性和真实任务结果改进，不以重构规模衡量质量。
- **成功率优先。** 成本优化必须在事先明确的任务集合和成功率门槛下评估，具体指标留待对应阶段定义。
- **按 Git 变更类型组织工作。** 从已核对的基线创建 feat/、fix/、doc/ 等分支，保留用户修改，显式暂存相关文件，验证后提交；不擅自推送或合并。
- **文档与开发同步。** 范围、决策、实现和验证结果发生变化时更新对应文档。
