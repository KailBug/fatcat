## 1. 已确认的产品边界

- Project 是显式实体，拥有稳定身份、项目工作目录和 Session 组织关系；相同目录不代表同一 Project。
- Project 内的新 Session 使用项目工作目录，不允许 Session 级目录覆盖；独立 Session 使用自己的目录。工作目录是文件操作与命令执行的默认基准，目录外访问仍由现有权限系统决定。
- 项目资料共享，Session 历史独立。加入 Project 不合并其他会话的历史，也不授予新的工具权限。
- 独立 Session 可从 Web UI 拖入 Project。迁入前提示已有上传资料将共享；目录不同则明确展示旧路径、新路径并确认。迁入不复制或移动工作目录文件，不改写历史消息及其中来源路径。
- 运行中或等待审批的 Session 先完成或取消操作，才能迁入；旧目录的待执行审批失效。记录目录变更，并在下一轮向模型说明。
- 资料的上传 Session 是来源信息；项目共享资料不能随上传者 Session 删除而自动销毁。资料关联与原件的实际实现属于阶段 2。

本阶段的可用闭环是创建项目、在项目内创建多个 Session、各自执行和保存，重启后恢复正确归属及目录，并允许确认后的独立 Session 迁入。附件、Memory、检索不作为本阶段的验收前提。

## 3. 已实现的数据所有权与持久化

### 3.1 一处保存归属，一处保存项目目录

`src/project/` 只承担项目记录校验、持久化和具体迁入记录转换，不建立插件注册表或通用实体框架。SessionStore 解析归属，Manager 协调目标 Agent 准备、确认与提交。

| 数据 | 唯一持久所有者 | 当前内容 |
| --- | --- | --- |
| Project | ProjectStore | 版本、UUID、名称、规范工作目录、创建/修改时间、修订号 |
| Session 归属 | SessionRecord | 互斥的 `location`：独立会话保存 `kind: standalone` 与自己的 `workspace`；项目会话保存 `kind: project` 与 `projectId` |
| Session 原存储位置 | SessionRecord | 不随执行目录变化的 `storageWorkspace`；不代表归属或访问权限 |
| 目录/归属变更 | 同一 SessionRecord | 有界的已提交事件：旧/新归属、旧/新规范路径、时间、变更 ID，以及尚需在请求中说明的事件状态 |
| 实际执行位置 | 当次执行快照 | 从 Session 归属和 Project 记录解析；包含 Session ID、归属代次、项目 ID/修订及规范目录，不作为另一份持久权威目录 |

Project **不保存第二份可写 `sessionIds` 列表**；项目内会话由已有全局列表按 Session 归属派生。Session 也不保存一份可覆盖项目目录的字段。UI 摘要继续提供解析后的 `workspace`，同时提供 `projectId` 与可用状态，避免让所有视图各自猜测目录。

ProjectStore 位于已选择的 Session 存储根下的 `projects/`，每项目一个有界、版本化 JSON，采用原子发布与短锁。现有 Session 扫描仅访问 64 位哈希目录，该目录不会被误认为会话桶；`FATCAT_SESSION_DIR` 继续隔离测试/用户数据，不新增环境变量。运行时记录保留解析后的 `workspace`、项目名/修订或不可用原因；v2 编码剔除这些项目投影字段，只持久保存 `location` 和原存储桶。

项目目录由 Project 唯一管理，可通过项目菜单统一变更。选择与规范化使用 Windows 原生目录选择和 `canonicalWorkspace`。创建或改目录不自动新建、搬移或复制工作目录。新目录不存在、不是目录或不可访问时失败，项目记录不发布；同一路径可显式创建多个不同项目，身份仍不同。附件隔离已在阶段 2 单独验收。

### 3.2 旧 Session 兼容与格式升级

使用显式 Session **v2**，解码器同时支持 v1/v2。原因是旧 v1 解码器只返回已知字段：如果在 v1 中直接增加 `projectId`，旧程序可能忽略该字段后把项目会话当独立会话运行，破坏项目目录和共享范围契约。版本提升能让旧程序拒绝新格式。

1. 旧 v1 在读取时映射成独立归属，不推断 Project，不按路径自动归类；读取/列表不重写文件。
2. 完整保留 ID、名称、时间、history、attempt、automations、compaction、forkedFrom 和原 storage bucket。不能用成功历史重建记录而丢掉中断事实。
3. 第一次成功持久写入时沿原修订和原桶原子发布 v2，包括回合开始或 compact 的领取记录；原子发布失败保留之前版本。模型失败不降回 v1，而是保存完整 v2 中断记录。新会话直接使用 v2。
4. v2 显式保存原桶身份；Store 读取不能继续把有效项目工作目录当文件位置校验依据。Session 恢复时另行解析 Project，避免隐藏双写。
5. 缺失/损坏 Project 不降级成独立会话、不回退启动目录。列表和历史可呈现“项目不可用”，执行、新建项目会话、上传及模型请求均停止，并说明修复对象。
6. v2 不是对旧版本的可写兼容格式；上线时说明旧程序无法打开已升级的会话。不要自动回写 v1，也不要把备份或导出当作已存在功能。
7. `--no-session-persistence` 维持独立进程内会话；阶段 1 拒绝与持久 Project 选择混用，不把临时会话悄悄注册进项目。程序化普通 `Session` 保持原入口。

只读旧格式兼容不等于支持新旧程序同时修改同一存储根。实施升级前应关闭旧实例；已启动的旧版本不知道新归属和操作领取协议，不能宣称混用版本已满足新的跨进程约束。

### 3.3 锁、修订和失败语义

项目会话数量从 Session 归属派生，不维护第二张成员表。阶段 1 迁入只改 SessionRecord；阶段 2 有附件时通过恢复日志共同发布归属和资料关联。跨进程提交在持久锁内再次核对 Session 修订、running owner 和资料范围修订，不能只依赖提交前的 `available()`。

Project 元数据短锁用于项目创建/修改及关联发布时的存在性和预期修订检查。阶段 2 锁序扩展为 **共享 metadata gate → Project 元数据锁 → Session 存储桶锁**，Session/附件读写先恢复未完成的已决定事务。不在锁内等待用户确认、模型或流式网络；维持短锁、显式冲突及保守陈旧锁边界，不引入通用事务框架。

准备阶段拿到的 UI 项目/会话修订只用来形成预览；提交时重新加载并核对。归属变化、项目变化、被删目标、并发回合开始或重复请求不能覆盖较新记录。项目内新建/恢复后第一次执行也要解析最新归属，领取回合时验证相关修订；旧进程不能继续按缓存的独立目录执行迁入后的会话。

普通回合使用 `attempt.ownerPid` 持久标记执行中；手动 compact 现在先保存 `activeOperation`，记录类型、PID、唯一领取 ID 和时间。Store 在同一桶锁内核对修订和领取，迁入/删除/其他写入不能覆盖活跃普通回合或压缩。成功、失败、取消均凭自身领取收尾；收尾保存失败时 runtime 保留 `pendingSettlement`，后续运行或管理操作先重试同一份收尾，失败则继续拒绝切换。崩溃后仅核查 owner 已退出，不恢复模型调用。真实第二个 Node 进程分别验证了 run/compact 的拒绝与取消后释放；PID 检查仍可能在崩溃后遇到 PID 重用而保守误判，不是 OS 级进程出生身份验证。

若项目目录和目标 Agent 准备失败，保留原 Session 与当前选中项；若保存失败，不发布新活动状态。若落盘成功但 HTTP 答复丢失，用 Session ID/修订/变更 ID 重新读取已提交结果，不再次追加迁入事件。将当前已经归属目标 Project 的相同请求识别为完成状态；其他修订冲突需要刷新确认。用户看到的成功必须来自持久提交。

追加的项目管理在同一 metadata gate 与 Project 锁下重新发现成员、核对资料集合及预览，不以 UI 显示“空”作为删除依据。ProjectStore 对外读取也先完成恢复；内部明确使用已持锁入口，避免重复获取 gate。批量修改和删除通过现有恢复日志发布，边界与限额见第 8 节。

## 4. 迁入的完整流程

### 4.1 预览与确认

1. 入口提交明确的 Session ID 与目标 Project ID，不使用“当前选中会话”替代源身份。拖放和菜单/键盘入口调用同一服务。
2. Manager 校验宿主空闲，加载源记录和目标项目。源正在运行（包括另一进程）或等待审批时拒绝；不先强制取消再迁入。
3. 解析旧目录、新项目目录，准备新 Tools/Skills/Agent。构建有界预览：源/目标名称与 ID、两条完整规范路径、资料共享提示、已有自动任务影响、预期修订。
4. 总是提示“该会话已有上传资料将归项目共享；历史不合并”。不同目录时必须由用户确认路径变化；建议相同目录也对资料共享变化进行明确确认。取消、关闭弹窗或目录窗口取消均无持久变更。
5. 提交携带源/目标 ID、预览修订和明确确认结果。服务端重新校验完整操作，不信任客户端自行声明“目录没变”。路径或共享范围已变化则旧确认作废，刷新预览。

阶段 2 预览已读取真实资料数量、scope revision 和集合指纹，展示共享影响；期间上传/移除后旧确认失效。迁入确认是产品组织操作的确认，不是 write/shell/browser 的授权。

### 4.2 原子提交与下一轮

已持久化 Session 迁入时，单次保存归属、目录变更事件、更新时间以及已确认的自动任务处理结果；原 history 和历史来源路径逐字保留，原存储桶不搬动。只在持久成功后刷新活动 runtime、Tools、Skills 和 UI。迁入未选中会话不切换当前历史；迁入选中会话保留该 ID 和历史视图，显示新的项目与目录。

无历史、无资料且 revision 为 0 的 Web UI 草稿沿用延迟保存：选择/迁入 Project 或浏览已有项目资料只更新/使用内存绑定，不因此创建空 Session 文件。首轮领取、显式命名或 fork 等首次写入重新校验项目后保存。阶段 2 成功上传时共同发布发起草稿与原件；取消/失败不保存草稿，不能把收到部分字节当成已接受资料。

阶段 2 已以 `src/attachments/transaction.ts` 的短锁和恢复日志替代有资料时的单快照提交：私有关联持久晋升项目，不经上传者动态推导共享，删除上传者不丢资料。异步上传绑定发起 Session、归属代次和目标；提交前目标迁入、改目录或删除会拒绝旧传输。未保存草稿的范围变化用可撤销的进程内 scope token 同样校验；单纯切换 UI 保留原草稿上传目标。细节与故障验收见附件架构。

回合开始前捕获本轮实际 Session 的归属和目录。下一轮请求中加入受控的变更说明：旧路径、新路径、共享范围、旧路径属于历史数据、目录文件未移动、旧工具结果不等于当前文件状态、需要重新检查文件后操作。路径必须作为转义数据展示，不能成为拼接后的任意指令；项目名也不成为 system 规则。

通知使用 AgentSession 的请求投影边界，不伪造用户消息、不改写原历史、不把消息摘要当权威配置。成功回合提交时确认已应用的变更事件；取消、模型失败或保存失败时保留待说明状态，重启和 compact 后仍可说明。多次空闲变更时保留可追溯的有界记录，并至少明确本轮最终目录及所有尚未说明的变化；达到限额必须明确报错，不静默丢弃尚未通知的事件。

原审批协调器在取消时 deny，并通过唯一 approval ID 拒绝旧答复。迁入提交再次确认不存在活动/待批操作，清理失效 UI 状态；恢复、切换或迁入不恢复任何过去的 approval。未来若允许更复杂并发，审批需绑定 Session/归属代次；阶段 1 继续单活动回合，无需新增审批队列。

### 4.3 已有自动任务与子任务

源码当前按 workspace 发现任务和持有调度租约。这不是 Project 关系，也不是资料访问依据。阶段 1 保留现有发现范围，避免顺带改变旧独立会话的调度行为；后台任务执行仍逐一解析其绑定 Session 的项目/私有范围，不能复用 UI 当前会话的范围。

迁入时将已有自动任务随同归属**原子暂停**，预览明确提示后由用户审阅并恢复。原因是即使目录相同，未来共享资料范围也会扩大；目录不同则旧任务 prompt、相对路径和文件基线可能指向另一批内容。不会改写历史任务 prompt、不重置 runs/过期时间、不补跑迁入期间事件。任务签名携带 `locationRevision`，旧排队激活即使在任务重新启用后也被拒绝。

无论采用哪种已确认策略，任务签名/激活都要包含绑定 Session 和归属代次，迁入使旧队列与文件基线失效；执行前重新校验，不消耗模型请求后才发现目标变了。同目录不同 Project 的任务可以使用同一目录调度租约，但必须使用各自执行身份。子任务继承父回合捕获的身份、目录、权限与额度，不查询 UI 选择，不自行扩大范围。

`workspaceAgentFactory` 的目录级 Tools/journals 继续保存文件执行事实；`createAgent.forSession` 在 Session 装配时绑定父子模型和附件访问器，保留调用方模型覆盖与预算。`withSessionIdentity` 只投影请求，不改历史。阶段 2 的 read 实际调用 Store 校验该身份，已用后台父子任务读取授权资料/拒绝另一项目已知引用验证，不把模型提示当授权。未增加 Memory/RAG 插件接口。
