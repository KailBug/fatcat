# Project 与 Session 关联：阶段 1 设计

状态：2026-10-13 设计与验收计划，**尚未实现**。本轮只核对源码和更新文档，不添加配置、依赖、功能代码或数据库。以下区分源码事实、用户已确认边界和建议方案；阶段编号指 [资料与 RAG 计划](RAG.md)，不替代已有工程阶段编号。

## 1. 已确认的产品边界

- Project 是显式实体，拥有稳定身份、项目工作目录和 Session 组织关系；相同目录不代表同一 Project。
- Project 内的新 Session 使用项目工作目录，不允许 Session 级目录覆盖；独立 Session 使用自己的目录。工作目录是文件操作与命令执行的默认基准，目录外访问仍由现有权限系统决定。
- 项目资料共享，Session 历史独立。加入 Project 不合并其他会话的历史，也不授予新的工具权限。
- 独立 Session 可从 Web UI 拖入 Project。迁入前提示已有上传资料将共享；目录不同则明确展示旧路径、新路径并确认。迁入不复制或移动工作目录文件，不改写历史消息及其中来源路径。
- 运行中或等待审批的 Session 先完成或取消操作，才能迁入；旧目录的待执行审批失效。记录目录变更，并在下一轮向模型说明。
- 资料的上传 Session 是来源信息；项目共享资料不能随上传者 Session 删除而自动销毁。资料关联与原件的实际实现属于阶段 2。

本阶段的可用闭环是创建项目、在项目内创建多个 Session、各自执行和保存，重启后恢复正确归属及目录，并允许确认后的独立 Session 迁入。附件、Memory、检索不作为本阶段的验收前提。

## 3. 建议的数据所有权与持久化

### 3.1 一处保存归属，一处保存项目目录

建议新增具体的 `src/project/` 模块，只承担已经需要的项目记录校验、持久化和目录解析，不建立插件注册表或通用实体框架。

| 数据 | 唯一持久所有者 | 建议内容 |
| --- | --- | --- |
| Project | ProjectStore | 版本、UUID、名称、规范工作目录、创建/修改时间、修订号 |
| Session 归属 | SessionRecord | 互斥的 `location`：独立会话保存 `kind: standalone` 与自己的 `workspace`；项目会话保存 `kind: project` 与 `projectId` |
| Session 原存储位置 | SessionRecord | 不随执行目录变化的 `storageWorkspace`；不代表归属或访问权限 |
| 目录/归属变更 | 同一 SessionRecord | 有界的已提交事件：旧/新归属、旧/新规范路径、时间、变更 ID，以及尚需在请求中说明的事件状态 |
| 实际执行位置 | 当次执行快照 | 从 Session 归属和 Project 记录解析；包含 Session ID、归属代次、项目 ID/修订及规范目录，不作为另一份持久权威目录 |

Project **不保存第二份可写 `sessionIds` 列表**；项目内会话由已有全局列表按 Session 归属派生。Session 也不保存一份可覆盖项目目录的字段。UI 摘要继续提供解析后的 `workspace`，同时提供 `projectId` 与可用状态，避免让所有视图各自猜测目录。

ProjectStore 建议位于已选择的 Session 存储根下的 `projects/`，每项目一个有界、版本化 JSON，复用原子发布与短锁方式。现有 Session 扫描仅访问 64 位哈希目录，该目录不会被误认为会话桶。这样 `FATCAT_SESSION_DIR` 继续完整隔离测试/用户数据，不新增尚不可用的环境变量。此位置是实施建议，不代表当前程序已创建它。

阶段 1 推荐项目目录创建时固定；是否首版开放项目级重定位仍待用户决定，不能把本建议当作已确认需求。选择与规范化使用现有 Windows 原生目录选择和 `canonicalWorkspace`。创建 Project 不自动新建、搬移或复制工作目录。目录不存在、不是目录或不可访问时创建失败，项目记录不发布；同一路径可显式创建多个不同项目，仍按项目 ID 隔离资料。

### 3.2 旧 Session 兼容与格式升级

建议采用显式 Session **v2**，新解码器同时支持 v1/v2。原因是旧 v1 解码器只返回已知字段：如果在 v1 中直接增加 `projectId`，旧程序可能忽略该字段后把项目会话当独立会话运行，破坏项目目录和共享范围契约。版本提升能让旧程序拒绝新格式。

1. 旧 v1 在读取时映射成独立归属，不推断 Project，不按路径自动归类；读取/列表不重写文件。
2. 完整保留 ID、名称、时间、history、attempt、automations、compaction、forkedFrom 和原 storage bucket。不能用成功历史重建记录而丢掉中断事实。
3. 第一次成功持久写入时沿原修订和原桶原子发布 v2，包括回合开始或 compact 的领取记录；原子发布失败保留之前版本。模型失败不降回 v1，而是保存完整 v2 中断记录。新会话直接使用 v2。
4. v2 显式保存原桶身份；Store 读取不能继续把有效项目工作目录当文件位置校验依据。Session 恢复时另行解析 Project，避免隐藏双写。
5. 缺失/损坏 Project 不降级成独立会话、不回退启动目录。列表和历史可呈现“项目不可用”，执行、新建项目会话、上传及模型请求均停止，并说明修复对象。
6. v2 不是对旧版本的可写兼容格式；上线时说明旧程序无法打开已升级的会话。不要自动回写 v1，也不要把备份或导出当作已存在功能。
7. `--no-session-persistence` 维持独立进程内会话；阶段 1 拒绝与持久 Project 选择混用，不把临时会话悄悄注册进项目。程序化普通 `Session` 保持原入口。

只读旧格式兼容不等于支持新旧程序同时修改同一存储根。实施升级前应关闭旧实例；已启动的旧版本不知道新归属和操作领取协议，不能宣称混用版本已满足新的跨进程约束。

### 3.3 锁、修订和失败语义

迁入只改变 SessionRecord，项目会话数量从记录派生，因此无需“先改 Project 的成员表，再改 Session”双写。采用原 Session 临时文件＋rename；跨进程提交必须在桶锁内再次核对 Session 修订和 running owner，不能只依赖提交前的 `available()`。

新增 Project 元数据短锁用于项目创建/修改，以及关联发布时检查项目存在性和预期修订；若同时需要两个锁，固定顺序为 **Project 元数据锁 → Session 存储桶锁**。不在锁内等待用户确认、模型或网络；与原来的短锁、显式冲突和保守陈旧锁处理保持一致。不新增复杂事务调度器。

准备阶段拿到的 UI 项目/会话修订只用来形成预览；提交时重新加载并核对。归属变化、项目变化、被删目标、并发回合开始或重复请求不能覆盖较新记录。项目内新建/恢复后第一次执行也要解析最新归属，领取回合时验证相关修订；旧进程不能继续按缓存的独立目录执行迁入后的会话。

普通回合已通过 `attempt.ownerPid` 持久标记执行中，但当前 `AgentSession.compact()` 只保存修订，不写 running attempt；单进程 Manager 的 busy 不能证明另一进程没有正在压缩。阶段 1 需为这种非普通回合的长操作补充窄的持久领取（例如可选 `activeOperation`，只记录实际存在的操作类型、所有者 PID、唯一领取 ID 和时间），与迁入、回合开始使用同一 Session 桶锁和 CAS。迁入在锁内拒绝仍有活跃 owner 的普通回合或压缩；正常、失败、取消均按领取 ID 与修订核对并持久收尾，只能释放自己持有的领取。清理写盘失败必须报告并保守保持忙碌状态，不静默解锁或覆盖较新记录；存储恢复后可由原持有者重试收尾。崩溃后核查 owner 已退出，不恢复模型调用。不能将准备时的空闲检查与提交分离，也不新增通用作业系统。双进程压缩与迁入竞态必须验收。

若项目目录和目标 Agent 准备失败，保留原 Session 与当前选中项；若保存失败，不发布新活动状态。若落盘成功但 HTTP 答复丢失，用 Session ID/修订/变更 ID 重新读取已提交结果，不再次追加迁入事件。将当前已经归属目标 Project 的相同请求识别为完成状态；其他修订冲突需要刷新确认。用户看到的成功必须来自持久提交。

建议首版不开放项目目录修改或项目删除，避免空项目判断与并发迁入、批量目录变更同时进入交付范围；具体产品范围待确认。将来开放删除时必须在同一 Project 锁下检查无成员和无资料关联，所有加入/新建路径遵守同一锁序；不能以 UI 显示“空”作为删除依据。

## 4. 迁入的完整流程

### 4.1 预览与确认

1. 入口提交明确的 Session ID 与目标 Project ID，不使用“当前选中会话”替代源身份。拖放和菜单/键盘入口调用同一服务。
2. Manager 校验宿主空闲，加载源记录和目标项目。源正在运行（包括另一进程）或等待审批时拒绝；不先强制取消再迁入。
3. 解析旧目录、新项目目录，准备新 Tools/Skills/Agent。构建有界预览：源/目标名称与 ID、两条完整规范路径、资料共享提示、已有自动任务影响、预期修订。
4. 总是提示“该会话已有上传资料将归项目共享；历史不合并”。不同目录时必须由用户确认路径变化；建议相同目录也对资料共享变化进行明确确认。取消、关闭弹窗或目录窗口取消均无持久变更。
5. 提交携带源/目标 ID、预览修订和明确确认结果。服务端重新校验完整操作，不信任客户端自行声明“目录没变”。路径或共享范围已变化则旧确认作废，刷新预览。

阶段 1 尚无附件时提示应准确写明“以后上传的资料归项目共享；当前没有附件”。阶段 2 接入后预览应列已有资料数和共享影响；不能在尚无资料计数时虚构数量。迁入确认是产品组织操作的确认，不是 write/shell/browser 的授权。

### 4.2 原子提交与下一轮

已持久化 Session 迁入时，单次保存归属、目录变更事件、更新时间以及已确认的自动任务处理结果；原 history 和历史来源路径逐字保留，原存储桶不搬动。只在持久成功后刷新活动 runtime、Tools、Skills 和 UI。迁入未选中会话不切换当前历史；迁入选中会话保留该 ID 和历史视图，显示新的项目与目录。

无历史、无资料且 revision 为 0 的 Web UI 草稿沿用延迟保存：选择/迁入 Project 只更新内存绑定，仍校验目标、忙碌与确认结果，不因此创建空 Session 文件。首轮领取、显式命名或 fork 等首次持久写入重新校验项目存在性和归属/目录修订后原子保存；失败不发布持久列表项。阶段 2 成功接收附件何时保存草稿依该阶段规则处理，不能把未完成上传当作已接受资料。草稿取消或关闭不落盘。

此处“单快照提交”只覆盖尚无附件的阶段 1。阶段 2 加入资产后，迁入必须把已有私有资料关联持久晋升为 Project 所有，并与 Session 归属变化提供可恢复的一致提交；不能仅在读取时沿 `uploaderSessionId → projectId` 推导共享，否则删除上传者会丢失所有权。届时需扩展存储提交协议和故障注入验收，未完成之前不允许带附件迁入。异步上传绑定发起时的 Session、归属代次和目标；提交前若归属变化就拒绝完成并清理临时数据，不默默改投新项目。资产事务属于阶段 2，本阶段不提前搭建空实现。

回合开始前捕获本轮实际 Session 的归属和目录。下一轮请求中加入受控的变更说明：旧路径、新路径、共享范围、旧路径属于历史数据、目录文件未移动、旧工具结果不等于当前文件状态、需要重新检查文件后操作。路径必须作为转义数据展示，不能成为拼接后的任意指令；项目名也不成为 system 规则。

通知使用 AgentSession 的请求投影边界，不伪造用户消息、不改写原历史、不把消息摘要当权威配置。成功回合提交时确认已应用的变更事件；取消、模型失败或保存失败时保留待说明状态，重启和 compact 后仍可说明。多次空闲变更时保留可追溯的有界记录，并至少明确本轮最终目录及所有尚未说明的变化；达到限额必须明确报错，不静默丢弃尚未通知的事件。

原审批协调器在取消时 deny，并通过唯一 approval ID 拒绝旧答复。迁入提交再次确认不存在活动/待批操作，清理失效 UI 状态；恢复、切换或迁入不恢复任何过去的 approval。未来若允许更复杂并发，审批需绑定 Session/归属代次；阶段 1 继续单活动回合，无需新增审批队列。

### 4.3 已有自动任务与子任务

源码当前按 workspace 发现任务和持有调度租约。这不是 Project 关系，也不是资料访问依据。阶段 1 保留现有发现范围，避免顺带改变旧独立会话的调度行为；后台任务执行仍逐一解析其绑定 Session 的项目/私有范围，不能复用 UI 当前会话的范围。

建议迁入时将已有自动任务随同归属**原子暂停**，预览明确提示后由用户审阅并恢复；这是待确认的产品选择。原因是即使目录相同，未来共享资料范围也会扩大；目录不同则旧任务 prompt、相对路径和文件基线可能指向另一批内容。不会改写历史任务 prompt、不重置 runs/过期时间、不补跑迁入期间事件。不能仅重新校验 file_changed 路径存在就认定任务语义不变。

无论采用哪种已确认策略，任务签名/激活都要包含绑定 Session 和归属代次，迁入使旧队列与文件基线失效；执行前重新校验，不消耗模型请求后才发现目标变了。同目录不同 Project 的任务可以使用同一目录调度租约，但必须使用各自执行身份。子任务继承父回合捕获的身份、目录、权限与额度，不查询 UI 选择，不自行扩大范围。

`workspaceAgentFactory` 的目录级 Tools/journals 只继续保存文件执行事实；归属数据放在每次 Session 装配/回合上下文中。当前 `src/agent.ts` 在 Session 绑定之前构建父子模型，子任务直接使用传入的基础 Tools；因此阶段 2 加入资料访问时，不能只包装 AgentSession 外层工具，必须让父子装配接收同一已绑定的执行身份。阶段 1 只传递实际需要的身份和目录，不预先添加附件仓库、Memory 插件或 RAG 接口。

## 5. 操作行为与真正待定的产品问题

以下“推荐”不是已获用户确认的行为。创建、项目内新建/恢复、独立 Session 迁入以及强制项目目录已确认；其余选择可分开决定，不能通过隐含默认造成资料扩散。

| 操作 | 阶段 1 最小范围 / 推荐 | 待确认问题及影响 |
| --- | --- | --- |
| 项目内新建、`/new` / reset | 项目入口新建明确带 projectId；当前项目会话中新建继承项目；显式“独立会话”入口新建私有会话。命令解析在所有入口共用核心 | UI 名称和命令拼写属于常规实现选择，不需要用户逐项决定 |
| fork | 推荐继承源归属与目录，复制当前既有成功历史/compaction，保留现有中断提示语义；不复制自动任务。fork 属于显式历史复制，不等于项目自动共享历史 | 阶段 2 单独定义私有资料引用的复制关系；项目资料仍由项目持有 |
| 解除项目关联 | 推荐首版不开放，直到语义确认。推荐变成独立会话并保留离开时的项目目录，不自动恢复迁入前旧目录；已共享资料和项目 Memory 留在项目，离开后不能继续读取，历史引用可标“当前不可访问” | 是否要求带走资料；如需带走，应单独选择并复制/授权，不能把整个项目资料自动私有化 |
| Project A → B | 建议首版拒绝直接跨项目拖动。推荐未来允许显式迁移 Session 历史/后续目录，但不自动把 A 的共享资料带入 B | 历史可能已包含 A 的资料内容，操作需要明确提示；哪些原件需要另行复制由用户选择 |
| 项目改工作目录 | 建议首版创建后固定。推荐后续在无活动/待批操作时项目级变更，逐会话记录待通知、暂停自动任务，不提供会话级覆盖 | 是否需要首版支持外部目录改名/移动后的重定位；这是项目级能力，不能用 `/workspace` 绕过 |
| 删除 Project | 建议首版不提供。推荐后续先允许归档；永久删除要求显式处理成员、资料和历史引用 | 是否保留会话、共享资料和可恢复期限，属于数据生命周期产品决策 |
| 迁入时已有自动任务 | 推荐原子暂停并提示重新审阅，阶段 1 开发前确认 | 直接继续可能把旧任务应用到新目录/更大资料范围；拒绝全部迁入又会降低可用性 |

阶段 1 可在未开放解除/跨项目/删除的情况下形成闭环，但这些限制必须在界面和使用文档中明确；后续不能用“先解除再迁入”绕过尚未决定的资料处理语义。

恢复已有项目会话时 `--workspace` 不能覆盖项目目录；推荐若用户显式同时传入不一致路径则报用法错误，路径一致也按 Project 解析。裸启动目录不参与覆盖。项目内 `/workspace` 可查看，修改明确拒绝并指向项目设置；服务端同样拒绝直接 API 修改。旧独立会话的目录选择行为保留。

## 7. 可执行验收计划

阶段 1 实施后执行 `pnpm run typecheck`、`pnpm run build`、`pnpm test`；新增浏览器验证复用本机 Edge 与注入模型，并运行相关现有 `pnpm run verify:sessions` / `pnpm run verify:webui` 回归。命令是未来计划，本设计轮没有执行这些检查，也没有发起真实模型请求。

每个用例使用独立临时数据根和目录 A/B；断言落盘 JSON、实际工具路径、请求投影和界面状态，不能只检查成功 toast。故障注入应覆盖真正的保存/竞态边界，不写与实现逐句重复的测试。

| ID | Given / When | Then（通过条件） |
| --- | --- | --- |
| P1-01 旧数据 | 给定 v1 正常/带 compaction/中断/自动任务快照，列表与恢复；分别注入开始保存失败和模型失败 | 只读不改磁盘；归属全为独立；首次持久领取成功即升 v2 并保留原字段/历史/原桶；原子保存失败不留下部分 v2，模型失败仍保存 v2 中断事实；旧 v1 程序拒绝 v2 |

| P1-11 草稿/新建/fork | Web UI 草稿选择/迁入项目，取消；再测试首次失败回合、显式命名、项目/独立 fork 和普通 Session 删除 | 草稿选择不落盘；首次持久写入重验项目，首轮领取前保存，显式命名/fork 不等待首轮；重启归属正确，失败无半记录；fork 不复制自动任务；删除 Session 不删除 Project 或其他历史 |

| P1-13 入口一致 | CLI/chat/TUI 新建和恢复同一项目；Web 两标签拖放、菜单、键盘确认、窗口取消、刷新 | 同一服务端关系和实际目录；不同标签的旧预览拒绝；未选中会话迁入不切换当前历史；移动端菜单可完成同一操作 |
| P1-14 不支持操作 | 采用首版推荐范围时，尝试解除关联、跨项目拖动、项目目录修改、项目删除和无持久化项目选择 | 明确限制且无数据变更；未开放能力不能通过私有 API 或组合操作绕过；产品范围改变后先更新对应验收 |

阶段 1 的资料隔离只能验证执行身份和后续接缝，不能把这些测试宣称为附件隔离已通过；文件共享、删除上传者后的原件保留、来源引用、fork 资料规则在阶段 2 用真实附件 fixture 再验收。阶段 2 另须注入“资产晋升与归属发布之间崩溃”、迁入时删除上传者、上传过程中切换 UI、上传期间真实迁入等情形：要么保留完整旧状态，要么恢复完整已确认的新状态，不出现私有原件意外共享、项目资料依赖上传者存活或结果落到当前 UI 会话。
